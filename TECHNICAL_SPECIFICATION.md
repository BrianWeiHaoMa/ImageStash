# ImageStash — Technical Specification

## Authority

`PRODUCT_SPECIFICATION.md` outranks this document. This document ranks second and outranks every other document, decision, and line of code in this project. Product decisions are not restated here: this document is read together with `PRODUCT_SPECIFICATION.md`, never instead of it. `Approach`, `Foundations`, `Composition`, `State`, `Standing rules`, and `Product decisions settled here` hold unconditionally and are checked by reading the built system. `How the guarantees hold` is true while the system runs, for every run inside the product's operating envelope and inside `Substrate assumptions`; where an entry names a limit, the limit is part of the decision. Unassigned implementation choices are deliberately open for downstream work at its own level. An explicitly pending decision remains with its named owner and is not a delegated choice. Work that finds a line here unworkable stops the dependent work and reports the conflict and a proposed amendment; independent work continues. It does not work around the line or add an assumption to make a failure disappear. A conflict that reaches a product line is resolved by amending `PRODUCT_SPECIFICATION.md` first. Labels (`S1`, `R1`, `P1`, `T1`) are permanent and are how plans cite this document.

## Approach

ImageStash is one desktop process that owns one folder. The record of truth is that folder's original files plus one SQLite store holding everything else about an item; the finished picture of an edited item is a render that can always be redone from the original and the layers, kept as a file only because the grid and every handoff read it. Every change lands through two kinds of step only, a transaction on the store and a rename of a whole file into place, ordered so that a kill at any moment leaves the change absent, complete, or finishable from the store at the next start. Windows is reached only through a second assembly of seams; everything else is portable code that never names Windows.

One process runs per Windows session. Inside it one UI thread owns every window, one thread owns the store, and pooled worker threads decode, draw, encode and grab the screen; at most one capture, one recording and one edit are in progress at a time.

## Foundations

- **.NET 10**, long-term support, published self-contained for win-x64 as one folder (F1), the folder the release's MSI installer puts on the PC. The portable assembly targets `net10.0`; the Windows assembly targets `net10.0-windows`.
- **Avalonia 12.1.4** with its Fluent theme (F2, F10): every window, the tray icon, the file pickers, the system theme.
- **SkiaSharp 3.119.4**, the version Avalonia.Skia 12.1.4 depends on, used directly: it decodes all four formats frame by frame, draws the layers on screen and into the saved file, encodes PNG and JPEG, and names installed font families. One pixel engine for screen and file is what makes "as shown" (G21) hold by construction.
- **KGySoft.Drawing.Core 10.0.2**: writes GIF frame by frame to a stream, each frame with its own palette and delay, because SkiaSharp does not write GIF and a recording must reach disk as it is captured (R7). Its binaries carry no use restriction (KGy SOFT License 1.0).
- **Microsoft.Data.Sqlite 10.0.13** with its bundled SQLite 3.53.3: the metadata store. A change to several rows that is atomic across a kill (G28) would otherwise be a journal ImageStash wrote itself.
- The Windows API through P/Invoke and COM interop from the Windows assembly only; no WinForms, WPF or WinUI.

## Composition

Two assemblies. `ImageStash` holds every part below and the declaration of every seam; it never references the Windows assembly, a Windows API, or a Windows-only package. `ImageStash.Windows` holds the entry point and the seam implementations and nothing else (F13).

**Store.** Responsible for the stash folder, the metadata store and the settings file. Owns exclusively: the store file and its only connection; item identity; every file name inside the stash folder; the settings file; and every file in the folder root and `originals\`, which it alone creates, renames or removes. It allocates the `.work\` paths Media and Capture write into, keeps the Open with… copies under `%LOCALAPPDATA%\ImageStash\open-with\`, derives a finished picture's format from F3 and the original's record, and publishes a written file by renaming it. It writes the export file and replaces the folder from one (G36; `State` Export stash…, Import stash…). Boundary: in comes a written `.work\` file with the item's facts, or a change to an item's facts; back comes the item as recorded, or a failure. Queries return the items of a scope or a search ordered as G4 and G5 say, the tag counts, and whether an original with a given content hash exists (G12). It hands out no pixels.

**Media.** Responsible for pixels: decoding a file frame by frame with each frame's duration; drawing a layer list over a frame; encoding frames to PNG, JPEG or GIF; the content hash; the size estimate; the PNG bytes and the bitmap of a still for the clipboard; the font list through the Fonts seam. Owns exclusively the meaning of every layer in pixels, and the encoders. A frame is composed in this order: the trim selects frames of the original; the crop cuts the original's rectangle; hide, draw and text layers draw in list order inside it; a caption bar is added above the cropped picture, extending its height; Shrink scales the result; the footer states that result's size. Boundary: in goes a path, or a frame and a layer list; out come frames, or a rendered file at a `.work\` path Store allocated. A file whose bytes do not decode comes back as "unreadable" with the file name, never as an exception. A file it cannot open after G35's retries comes back as a failure naming the file and the reason, which is not "unreadable". Capture hands it full frames, each carrying its sample time, and the time of Stop; Media finds the changed rectangle and the delays itself and reports the bytes written so far. The size estimate is the byte length the encoder produces for the current layers: the whole picture for a still; for an animation, evenly spaced kept frames scaled to the kept count, the sample size being the implementer's (L2). A JPEG's or WebP's EXIF orientation is applied as the file is decoded (a PNG's is not read): its dimensions, frames, clipboard forms and renders are upright as the camera meant them while the file's bytes stay as they came (F3), and the original's pixel grid that every layer position names is that oriented grid.

**Capture.** Responsible for the frozen overlay on every display, the region drag, the screenshot, the recording loop with its frame and bar, and the cap. Owns the recording state and its frame queue. Boundary: Window starts a screenshot or a recording and gets back cancelled, or a written `.work\` file with its auto name (F12) for Store. Stop drains the queue, closes the last frame at the moment of Stop, then finalizes; a recording with no frame is cancelled; Cancel discards the queue; an encode failure cancels the recording and is named. Screens are read through the Screen seam; GIF frames are written through Media.

**Window.** Responsible for the stash window in both states, the grid, search and scopes, the preview, in-window notices, the Settings page, the notifications, the tray menu's actions, imports, pastes, Open with… and the handoff. Owns the selection, the paste target shown in the footer, and every clipboard write. Boundary: it calls Store, Media, Capture, Editor and the seams; nothing calls it.

**Editor.** Responsible for one edit session: the live layers, the five tools, the option row, undo and redo, Compare, the footer's size, Save, Save as new item, Revert and Cancel. Owns the session's undo stack. Boundary: opened on one item, it hands Store a layer list and the rendered `.work\` file (for Save as new item, also the new item's facts; Store copies the original). Save returns to Window the published item with its revision. Save as new item publishes the new item, tells Window its identity, and continues the session on it (G26). Cancel returns the discarded layer list for the notice's Undo. A Save is rendered, committed and published before the editor returns, showing a busy state meanwhile (G35). A Save with no layers on an unedited item changes nothing. The clipboard refresh after a Save (G26) is Window's, after the editor returns.

**Seams**, each declared in `ImageStash` and implemented only in `ImageStash.Windows`:

- *Tray*: icon, red dot, tooltip, menu, left click.
- *Shortcuts*: register and release four combinations; report "held by another program" or "types a character on the current layout"; report a keyboard-layout change.
- *Screen*: the displays with bounds in physical pixels; a grab of a rectangle, with the pointer drawn in when asked; marking a window excluded from capture.
- *Clipboard and drops*: write files plus, for one still, a PNG stream and a bitmap, remembering the identities written, or the search box's text alone; read, only when asked, either files-then-image, with the clipboard's text when it holds neither, or image-only, converting a DIB of any depth to the pixel contract; the sequence number; a drop's files, including files a browser hands over as streams; start a drag carrying files.
- *Target*: the paste target, with its app name. It is read synchronously as the foreground window when the open shortcut fires while ImageStash is not foreground. It is left unchanged when the shortcut fires while ImageStash is foreground, and when ImageStash shows its stash window again at the end of a capture (G3). When ImageStash is activated any other way, it is the window the seam's foreground hook reported just before ImageStash's own, passing over the shell's task switcher; while the hook has not delivered within 250 ms the reports queued before that read, it is none, and becomes that window once the late report comes while ImageStash's window is still in front. It is none when that window is ImageStash's own (a notification included), the desktop or the taskbar. For a handle Window passes back: whether it still exists, whether input may be sent to it, its caret rectangle or none, and activate it and send one Ctrl+V.
- *Quiet windows*: show a window without activating it; round a window's corners as Windows 11 rounds its own; the tray icon's rectangle.
- *Border drag*: a drag of the stash window's border by the user stops at the window's minimum, the opposite edge staying where it is, whichever edge or corner is dragged.
- *Recycle Bin*: recycle files and keep their recycled identities; permanently remove those recycled entries.
- *Start with Windows*: set or clear.
- *Fonts*: installed family names and whether a family is installed.
- *Dialogs and Explorer*: open and save pickers, the Open-with dialog, reveal a file, open a folder.
- *Locations*: the default stash and settings folders (F6).
- *One instance*: hold the session's instance; tell the running instance to show its window.

**Outside parts.** The paste target: any app window; it receives activation and one Ctrl+V and nothing else. The outside editor opened through Open with…: it rewrites the copy it was opened on, in place or by replacement, while ImageStash watches that copy. The Windows shell: owns the Recycle Bin's contents and File Explorer.

**What crosses every boundary.**

- Pixels: 32-bit BGRA, straight alpha, top-down rows packed without padding, sRGB, in physical pixels. A frame handed across a boundary is the receiver's until it hands it back.
- Times: UTC with millisecond precision in the store; local time in auto names and on screen. A frame's duration in milliseconds from the decoder. A GIF delay in centiseconds, taken as the difference between the two frames' times on the clip's timeline after each is rounded to the nearest centisecond, halves up, so rounding never accumulates.
- A layer list: ordered bottom to top. Every position, size and rectangle is given as integers on the original's pixel grid, origin top-left, a rectangle by its top-left and size, so a crop or Shrink never moves a layer and a crop can be widened later (G22). A text layer: the top-left and size of its box and its font size in those pixels; a caption bar: its font size in those pixels. A draw mark: a polyline (pen, marker), two end points (arrow) or a rectangle (box), with its color and one of three thickness steps. A hide layer: a rectangle with blur or black. A time range: the first and last frame index of the original, counted from zero, inclusive. Colors as 8-bit sRGB RGBA; an outline as a color, Auto or None; fonts by family name; rotation in degrees clockwise about the layer's centre; the trim as a frame range; Shrink as 1, 3/4 or 1/2.
- An operation's outcome: done, cancelled, or a failure naming the action, the subject (a file or item name) and the reason, in words, shown unchanged (G35). A failure after a commit (a file step, a clipboard write) carries the item as committed and leaves the commit in place.
- Item identity: an integer the store assigns once and never reuses; a file name is never identity.
- The paste target: its window handle and its app name, the executable's file description, else its file name without extension; for a window hosted by the application frame host, the hosted app's.

## State

**Record of truth.** The stash folder holds the store `stash.db`, each item's original, and the finished picture of each edited item: an unedited item's one file is in the folder root and is both; an edited item's original is in `originals\` and its finished picture in the root (F6). The finished picture can always be rendered again from the original and the layers. The settings file `%LOCALAPPDATA%\ImageStash\settings.json` is the record of truth for the shortcuts, the options, the theme, the stash location, the thumbnail size, the flyout size, and the pinned size and position. Everything else (thumbnails, decoded frames, any cache) is derived, lives in memory or under `%LOCALAPPDATA%\ImageStash`, and is never needed to open a stash (R8).

**The store.** One SQLite file in the DELETE journal mode, a rollback journal on disk, set and verified at every open and never WAL or an in-memory journal, so that a commit is atomic across a kill (S2) and between transactions the metadata is one file that Move copies as one. `user_version` carries F11's version; a build that finds a lower version migrates upward in one transaction before anything reads, and never writes a store it cannot read. One connection on one thread; every change is one transaction. Per item: identity, name, tags, favorite, added time, the original's and the finished picture's file names, the original's content hash, the layer list, a layer revision, the revision the finished file was rendered for, and the file steps still pending; per use, the item and the time (G10). A row marked deleted is returned by no query and reserves its file names until it is removed.

**Files.** A file enters the folder root or `originals\` only by a rename, from `.work\` inside the stash folder or from the other of those two places, on the same volume, so it appears whole or not at all (R2). `.work\` holds renders and recordings in flight and held copies. Nothing in it is an item; at start, after every pending step is resolved, anything in it that no row refers to is deleted.

**File names.** The finished picture's file is the item's name made safe for a Windows file name, with " 2", " 3" … while taken, plus the extension F3 gives its format. Names are compared as Windows compares file names, ignoring case, and a name Windows answers, or may come to answer, as another file's short 8.3 name counts as taken. An edited item's original keeps that name under `originals\` with its own extension. Rename renames the files (P1).

**Every change.** The transaction that commits an item's facts is where the change takes effect; success is shown only after the last step the change needs has completed (R9). A change that also moves files commits its remaining file steps in that transaction and clears them in a final one. At every start, before anything reads the stash, Store finishes or undoes every pending step from what is on disk, so a kill leaves each change absent, complete, or finished at the next start (G28); a window summoned meanwhile shows a busy state naming the opening and nothing of the stash (G35). A step still refused after G35's retries at start is undone instead: the change is rolled back to the facts the row kept for it and its files are put back, the failure is named, and every other item opens (G35); an undo refused in turn leaves the steps on the row, as `A live failure` says, for a later start, and every other item still opens. A Save whose new render has already replaced the earlier one has nothing to put back: it stays listed as saved on that render, the failure is named, and the next start finishes it.

- *Import, screenshot, recording, pasted image:* the file is written in `.work\`; the row is inserted with "rename into place" pending; the file is renamed; the step is cleared. At start, a row whose file is not in place is removed with its `.work\` file.
- *Save as new item:* Store copies the original into `.work\` and, when layers exist, takes the render Media wrote there; the row is inserted with both renames pending; the files are renamed, the original into `originals\` and the render into the root, or the copy alone into the root when there are no layers; the steps are cleared. At start, a row whose files are not all in place is removed with its `.work\` files and any file it had already published.
- *Save:* Media renders into `.work\`. The row commits the new layers, keeping the previous list until the rendered revision catches up, raises the layer revision and records the steps: move the original into `originals\` if it is still in the root; rename the render into the root under the finished picture's name (replacing an earlier render); set the rendered revision. At start, a row whose rendered revision is behind its layer revision is rendered again and finished. A Save with no layers is Revert to original on an edited item: the finished file is deleted and the original renamed back into the root, so the item has one file again (F7); on an unedited item it changes nothing. A replaced finished picture is not kept (G29).
- *Delete:* the files are copied into `.work\` as held copies; the rows are marked deleted with those copies recorded; the files are recycled through the Recycle Bin seam, which keeps each recycled identity while the notice shows. Undo renames the held copies back into place, removes the recycled entries, and clears the marks; expiry deletes the held copies and removes the rows. At start, a marked row's files are recycled if still present, its held copies deleted, and the row removed.
- *Rename:* the row commits the new name with the files' new names pending; the files are renamed; the step is cleared.
- *Tags, favorite, use:* one transaction each; a use is written after the clipboard write or the drop has completed, never before (G10).
- *Open with…:*
  - Opening: Store copies the finished picture, under its file name, into a new folder it creates for the session inside `%LOCALAPPDATA%\ImageStash\open-with\`, which itself always holds a file Store recreates at every start, so no stash Move chose can contain the copy (G30). The row records the open-with session with the copy's hash, the watcher is armed on that folder, and the dialog opens on the copy.
  - Classifying: when the dialog returns, and whenever the watcher reports a change, the copy is read for classification only once it opens without sharing, which fails while another program still holds it (retried for L2's duration, then at each later change and at least once a second until it opens). A difference from the recorded hash is a rewrite, whose hash becomes the recorded one, the session marked as awaiting adoption.
  - Adopting: once no edit is open on the item, the copy is read again as classifying reads it, and the bytes of that one read are hashed, decoded and copied into `.work\`; bytes whose hash differs from the rewrite's are a newer rewrite, taken in its place. Bytes that decode are adopted (G27): the row commits their `.work\` copy as the original under the item's name with its own format's extension (File names), records their hash as the session's and clears its awaiting mark, keeps the previous layer list and original file name as the item's one undo record, an earlier adoption's record first expired as *Undo and expiry* says, the adoption refused by name while that expiry is refused, and records the steps: move the root file into `.work\` as the held previous original when the item is unedited, or delete the render when it is edited; then rename the adopted file into the root. Bytes that do not decode are not adopted: their hash becomes the recorded one, the awaiting mark is cleared, and the failure is named.
  - Undo and expiry: Undo restores the previous original and layers from that record, renders the finished picture again, recycles the outside version (the adopted file), and clears the record; it is refused by name once a Save, a Revert or a later adoption of the item has followed the adoption (G27). Expiry, a refused Undo, a later adoption of the item, or the next start recycles the previous original (the held one, or the file in `originals\`) and clears the record. An adoption whose file steps a live failure stopped and a later change of the item's files finished (`A live failure`) completes inside Store without the notification: its record stands until the next start, or a later adoption of the item, recycles its previous original and clears it (G27).
  - Asked again: on an item whose copy no program has rewritten, Store copies the finished picture afresh into a new session folder, records that session, and deletes the old copy. The old copy is held without sharing from its classification until the new record is committed, and let go only to be deleted, so a rewrite landing between letting go and deleting is deleted unread or swept at the next start (G27). Asked again while a rewrite awaits adoption, Store keeps that copy and its session.
  - Start and end: every recorded session's copy is classified the same way before anything reads the stash, a copy still held after L2's duration being left to its later retries while the stash opens, and watched again. A session ends when its item is removed for good (its Delete's notice gone without Undo, or the start finishing that Delete); its copy is then deleted, with the session's folder when nothing else is in it.
- *Move:* it waits, as a busy state naming what it waits for (G35), while a capture, a recording, an edit, or another change's transaction or file step is in progress, or while a notice or notification whose Undo still stands shows. From the moment it is asked nothing else starts until it ends, in success or failure, other than a handoff, a `Ctrl+C` copy or a drag-out (G10), which start until the copy begins and are refused by name (G35) from then. The settings file records the chosen folder as a copy in progress. Every file and the store are copied into the chosen empty folder, leaving out that folder itself when it lies inside the old one, on the store's thread between transactions. The settings file is replaced with the new location and "previous folder pending removal" in one step, which ends the copy in progress. The old folder is removed, apart from the chosen folder and what it holds when it lies inside the old one; the field is cleared. A copy that fails deletes the partial copy, clears the copy in progress and changes nothing (G30). At start, the partial copy of a copy in progress is deleted and a pending removal is finished.
- *Export stash…, Import stash…:* both wait as Move waits and from the moment one is asked stop everything else the same way, on the store's thread between transactions. Export writes one ZIP archive through .NET's in-box `System.IO.Compression` (Zip64 where a file needs it): a manifest naming the format, the store's `user_version` and the build; every file of the folder root and `originals\` under its name; the store file (its journal, `.work\` and R8's derived data left out); and `settings.json` reduced to the values G36 names. While a change of an item's files that a live failure stopped has left steps on its row, Export first finishes or undoes those steps, as a later change of the item's files does (`A live failure`), and is refused by name, naming the item, only while one is still refused. The archive is written beside the chosen path and renamed over it (R2's rule), so a kill leaves no partial export at that path. Import reads the manifest first and refuses by name a file without one or whose store version is above this build's. It extracts everything into a new folder beside the stash folder, opening the extracted store to confirm it reads and migrates; drops the open-with sessions that store records, whose copies stay on the PC that exported it; and refuses by name, deleting the extracted folder, an archive missing a file that a row with no step pending and no deletion mark names. It then records "import pending" in the settings file, naming the extracted folder and the name the replaced folder will take; renames the stash folder away under that name, renames the extracted folder into its place, and recycles the renamed-away folder, the replaced stash's open-with sessions ending as a deleted item's do; replaces the settings G36 names with the archive's and clears the field; the Clipboard seam forgets the identities it wrote, which name items of the replaced stash; the stash opens again as at a start, its pending steps finished or undone before anything reads it, and the window lists it. At start, a pending import whose extracted folder is whole is finished from the step the names on disk show; while a step it needs is still refused, the field stays for a later start, the failure is named, and nothing of the stash opens until then; one whose extracted folder is not is deleted with the field cleared and the stash untouched (G28, G30).

**A live failure** (a refused write, or a file still held after G35's retries): the step stops, the failure is named, the pending steps stay on the row, and the next start finishes or undoes them. Meanwhile the grid shows the picture on disk, Edit opens on the layers that picture was rendered from, and no clipboard refresh (G26) happens. No other item is touched. A later change of the same item's files (a Save, Revert, Save as new item, Rename, Delete, Open with… adoption or its Undo) finishes or undoes those steps before it runs, rendering the finished picture again on the store's thread where a render is owed; a change of its tags, favorite or uses, which touches no file, leaves them to that change or the next start. G1 excludes that render from its one second.

**Settings** are written as a new file beside the old and renamed over it. A file from an earlier build is read by its version: a missing value takes its default and a value this build no longer keeps is ignored (G31). At every start, while Start with Windows is on, the user's Run entry is rewritten with the executable's current path, so a moved folder still starts, and while it is off the entry is removed (F1).

## How the guarantees hold

### G1. Within a second, beside the caret

The window is created at start and kept hidden; summon shows it. The paste target is the foreground window the Target seam reads at the press, or the one it already holds when ImageStash is foreground, so the press looks up only the caret: the Windows caret of the target's thread; else the accessibility caret object of the focused window; else, through UI Automation, the bounds of the focused text control's collapsed selection; else of that selection expanded to one character; else none. The lookup is abandoned after 250 ms in favour of the pointer. By construction. Limit: G1's own conditions: other programs not saturating the PC; no other program holding the store or its journal open, since a hot journal must be rolled back before any read, which needs the journal deleted (S2); and no render, owed by a Save or an Open with… Undo left unfinished, running on the store's thread before the next change of that item's files (`State` A live failure); and no start still opening the stash (`State` Every change, Open with… Start and end).

### G3. One instance

The One-instance seam holds a `Local\` named mutex for the process's lifetime; a second launch finds it held, signals a `Local\` named event, and exits; the running instance shows the window as a tray click would. By construction. Limit: E1, one session per user (S7).

### G8. The handoff

Window writes the clipboard through the Clipboard seam: the finished files as a file list (CF_HDROP); for one still also, from Media, its PNG bytes under the registered format "PNG" and a 32-bit CF_DIBV5 bitmap with alpha. With a target, Window hands the seam the handle it shows in the footer; the seam confirms the window still exists and that its process's integrity level is not above ImageStash's (a level it cannot read counts as above); Window hides the flyout; the seam activates that handle, waits, bounded, until it is the foreground window, and sends Ctrl+V. Any of these failing takes the "Copied · press Ctrl+V" path with the clipboard already written. A clipboard write that fails after its retries names the failure and nothing is sent. While the store cannot be read, the handoff and `Ctrl+C` hand over an item from Window's listing only while the store's in-memory counts show no commit since the item was listed and, for an item listed with file steps pending, no file step since that left a file of the root or `originals\` gone or replaced; any other item is refused by name (G35) until the store can be read again (G8). By construction. Failure direction: an app that takes the keystroke and ignores the paste looks delivered, and ImageStash never says so (G10); input the user gives in the instant between the check and the keystroke goes where the user sent it, and the paste keystroke with it. Limit: E6 (S6).

### G12. Duplicates

Store keeps a SHA-256 of each original; a candidate with an equal hash is compared byte for byte before being refused. By construction.

### G13. Pasting

Paste image and Ctrl+V read files-then-image: a file list, else the "PNG" format, else a DIB of any depth, else the clipboard's text, in one read; Stash clipboard image reads image-only: "PNG", else a DIB. What is found decides between an import, a PNG item, words into the search box or a tag field (Ctrl+V there alone) and the notice. By construction.

### G14, G15. Capture

The Screen seam grabs physical pixels from the desktop through GDI. A screenshot grabs every display once and the overlays show those grabs dimmed, so the screen is frozen by construction. A recording samples the region every 70 ms (the GIF timing nearest 15 per second, F3) on its own thread, draws the pointer when Settings says so, and passes frames through a bounded queue to an encoder thread that appends each to the GIF in `.work\`. Each appended frame is only the rectangle changed since the previous frame, with its own palette: the rectangle's own colours when one palette holds them, otherwise a median-cut quantization of those pixels, no dithering. Its delay is the time to the next sample (or to Stop) rounded as the boundary rule says, so playback lasts the recorded time. The frame, the bar and every notification are marked excluded from capture, which the desktop grab honours by showing what is beneath them (S4). The bar shows the bytes written so far. A sample taken while the queue is full is skipped and the previous frame's delay grows, as G15 says. By construction.

### G16. Notifications never take focus

Shown through the Quiet-windows seam without activation, topmost, without a taskbar button, above the tray icon's rectangle on the primary display, or above that display's bottom-right working-area corner when the rectangle cannot be read; a click into the name field activates the window, which is the user's act. By construction (S10).

### G18. Delete with Undo

Delete recycles the files after Store has held copies of them, and Undo restores from the held copies, so it does not depend on the bin; the deleted row keeps the paths free until the notice expires, and the recycled entries are removed on Undo. By construction (S9).

### G21. Fonts, colors and rotation as shown

One Media routine draws a layer list onto a Skia canvas; the editor's canvas calls it through Avalonia's Skia lease, and Save calls it onto a surface of the output size. A family the font manager does not match is drawn with the default typeface and reported, so the editor says so. Emoji, the Windows emoji panel's included, reach the layer's text field as typed text through Avalonia's text input and fall back glyph by glyph to an installed emoji font. By construction (R4, S11).

### G23. Black box leaves nothing

Every output frame is fully composed in memory before encoding; the box is an opaque fill; encoders see only composed pixels. By construction.

### G26. The clipboard after Save

The Clipboard seam renders every format when it writes, and remembers the sequence number after each write it makes and the identities it wrote. After a published Save, or a Rename whose files have moved, Window prepares the same items' current finished pictures, leaving out any item deleted since, and asks the seam to write them again; the seam does so only when, with the clipboard held open, the number is still unchanged and the identities include this one. A changed number is not a failure, and the refresh records no use (G10). The number is a counter, not clipboard data (N9). By construction (S14). Failure direction: a write another program makes, in the instant between ImageStash's close and its read of the number, is taken as ImageStash's own, and the next refresh replaces it. Limit: E3.

### G27. Open with…

The outside program is handed a copy outside the stash folder, so nothing but ImageStash writes inside it (E2); Window watches that copy through a file-system watcher from before the dialog opens until the item is removed for good, has it classified when the dialog returns and at every change, and a rewrite is adopted, or refused as unreadable, as `State` says. By construction.

### G28. Durability

State's ordering, SQLite's atomic commit (S2) and the rename rule (S1, R2). By construction. Failure direction: a change in flight at the kill is absent, or finished at the next start before anything reads the stash. Limit: E3.

### G29. Originals untouched

Store alone creates, renames or removes files in the root and `originals\`, and changes an original only by renaming it (Save, Revert, Rename, G27's adoption), recycling it (Delete, G27's Undo and expiry, Import stash…'s replacement) or copying it whole into the chosen folder before removing the old one (Move); Media opens every item file read-only (R3). Construction for the folder, discipline for the read-only open.

### G30. Move

The settings replacement is the one point of change; before it the old folder is whole and the new one disposable, after it the reverse. By construction.

### G33. Shortcuts

Each combination is registered as a system hot key; failure with "already registered" is "held by another program" (S5). A combination types a character when translating it under the foreground thread's keyboard layout, without touching keyboard state, yields a character or a dead key. That is checked at start, at every registration, whenever the foreground thread's layout, sampled once a second (S13), differs from the last sample, and once more when a hot key fires, before it acts. A combination failing a check is released at once and named with its reason in the tray tooltip, the reason giving way as G33 says when the tooltip cannot hold it beside every other failure named there, while every other function keeps working. By construction. Failure direction: a press within the second after a layout change is swallowed once and does not act. Limit: E3.

### G35. Retries, refusals, no crash

Every file open in Store and Media retries a sharing or lock violation for L2's duration before the failure is named, and a store transaction that fails because a file was held is retried whole within that duration. Every decode runs through Media's boundary, which turns a codec that rejects the bytes, or completes with missing data, or throws, into "unreadable", as it does a file that ends before its format's own end (PNG's IEND chunk, GIF's trailer, JPEG's end-of-image marker, the length WebP's RIFF header declares). Limit: S11, so a JPEG whose scan data stops at a marker before its scan is complete is read as the picture the codec completes, not refused.

### N3. Nothing sent

The Target seam sends one keystroke, Ctrl+V, after activation, and nothing else to any window (R6). By construction.

### N9. Clipboard reads

The Clipboard seam's read is called by exactly three actions (R5). By discipline.

### F13. Seams

The portable assembly references neither the Windows assembly nor a Windows-only package, and its code calls no Windows API, neither one .NET carries in-box nor one reached through platform invoke (R1). By discipline.

## Substrate assumptions

The arrangements above hold inside the product's operating envelope and these assumptions; outside either, nothing is promised.

- **S1.** A rename within one volume is either done or not done when the process is killed during it: on NTFS, probed (400 kills of a process looping write-then-replace, every destination whole, Windows 11 build 26200); on another local file system Windows mounts, granted, since Microsoft documents replacement by `MoveFileEx` but not its atomicity (MoveFileExW, 2023-06-01).
- **S2.** An SQLite transaction in the DELETE journal mode is atomic and durable across an application crash at any synchronous setting, while the operating system and the volume keep working (sqlite.org/pragma.html, "Transactions are durable across application crashes regardless of the synchronous setting or journal mode", SQLite 3.53.3); its Windows layer retries sharing and lock violations ten times over about 1.4 seconds (os_win.c, 3.53.3).
- **S3.** Microsoft.Data.Sqlite 10.0.13 runs on .NET 10 and its bundle supplies the native library for win-x64 (nuget.org, 10.0.13).
- **S4.** A grab of the desktop through `GetDC(NULL)` and `BitBlt` from a per-monitor-DPI-aware (version 2) process returns physical pixels across displays of different scaling (GetDC, 2021-10-13; High DPI Desktop Application Development, 2026-09-10) and omits a window whose display affinity is "exclude from capture", showing what is beneath it (probe on Windows 11 build 26200; SetWindowDisplayAffinity, 2024-02-22, Windows 10 version 2004 and later, while the desktop is composed).
- **S5.** `RegisterHotKey` fails with error 1409 when another thread or program holds the combination, except that a default hot key Windows registers, such as PrintScreen opening the Snipping Tool, may be overridden while one of the registering app's windows is in the foreground (RegisterHotKey, 2025-07-01, which names no error code; 1409 by probe on Windows 11 build 26200), and `ToUnicodeEx` with flag 4 translates a combination without changing keyboard state (ToUnicodeEx, 2023-02-02).
- **S6.** Injected input reaches only windows of equal or lower integrity (SendInput, 2021-10-13), `SetForegroundWindow` returns zero when it did not bring the window forward (2025-10-06), and a process's integrity level is readable with limited query access to a process of the same account (OpenProcessToken, 2022-09-23).
- **S7.** A kernel object named with the `Local\` prefix is scoped to the caller's Windows session (Kernel object namespaces, 2024-05-07).
- **S8.** The current user's `Run` key starts its entries at that user's sign-in, except when Windows starts in Safe Mode, and is writable without administrator rights unless its permissions were changed (Run and RunOnce Registry Keys, 2026-02-21; the key's permissions on Windows 11 build 26200, read unelevated, give the signed-in user full control).
- **S9.** `IFileOperation` with recycle-on-delete sends a file to the Recycle Bin and reports the recycled item to the progress sink, or reports none when the file was deleted for good instead (G29), and deletes a given shell item (SetOperationFlags, 2021-10-13; PostDeleteItem, 2024-02-22, "If the item was fully deleted, this value is NULL"; DeleteItem, "Declares a single item that is to be deleted").
- **S10.** Avalonia 12.1.4 on Windows shows a hidden window in its normal state without activating it when `ShowActivated` is false, gives its tray icon a left-click event, a right-click menu and live icon and tooltip updates, requests per-monitor DPI awareness version 2 and reports positions and screen bounds in physical pixels, lets a control draw on an SkiaSharp canvas through its Skia lease, changes decorations and taskbar presence on a shown window, and delivers browser virtual files through its drop API (Avalonia source at tag 12.1.4; the lease is marked unstable).
- **S11.** SkiaSharp 3.119.x decodes PNG, JPEG, GIF and WebP including every frame of an animation with its duration, with WebP built into its Windows binary; encodes PNG and JPEG and not GIF, its JPEG encoder (libjpeg-turbo, `JPEG_MAX_DIMENSION` 65,500) writing a side of at most 65,500 and faulting the process when asked for more (probe on this PC with SkiaSharp 3.119.4, 2026-10-22), so a larger side is refused before it is called, its JPEG decoder refusing a side over 65,500 as invalid input, so such a JPEG is unreadable (probe on this PC with SkiaSharp 3.119.4, 2026-11-06), and its PNG encoder and decoder (libpng at its default user limit) writing and reading a side of at most 1,000,000, the encoder writing nothing when asked for more (probe on this PC with SkiaSharp 3.119.4, 2026-10-22), so a larger side is refused before it is called and a PNG with a larger side is unreadable; returns null from its font manager for a family that is not installed; and honours its documented contract on malformed input, a null codec or a result code, except that a truncated animated WebP decodes as the frames it still holds, with success, and a JPEG whose entropy-coded data stops at a marker before its scan is complete decodes with success, libjpeg's warning surfaced by nothing, the block where the data stops decoded as if the missing bits were zero (a pattern or coloured noise) and, in a single-scan JPEG, every block after it mid-grey (mono/SkiaSharp source at v3.119.4; probe on this PC with SkiaSharp 3.119.4, garbage, truncated and marker-cut input). A decoder defect that faults the process instead is outside this assumption.
- **S12.** KGySoft.Drawing.Core 10.0.2 appends frames to a GIF stream one at a time, each with its own delay in centiseconds and its own palette with a transparent entry, and quantizes by median cut, octree or Wu, or to a palette the caller gives; its median cut can merge a colour a few pixels carry into another though every colour would fit one palette (docs.kgysoft.net, 10.0.2; source at v10.1.0; probe on this PC, 2026-10-22).
- **S13.** `GetKeyboardLayout` returns the active input locale identifier of a given thread (GetKeyboardLayout, "Retrieves the active input locale identifier (formerly called the keyboard layout)", "The identifier of the thread to query").

- **S15.** An out-of-context foreground event hook delivers foreground changes to the registering thread's message loop without a DLL in other processes (SetWinEventHook, 2021-10-13). ## Standing rules

- **R1.** Only `ImageStash.Windows` references a Windows API or a Windows-only package; `ImageStash` never references it, and a seam gains no member another platform could not implement.
- **R2.** An item's file is created only at a `.work\` path Store allocated, and reaches the folder root or `originals\` only by rename, or as Move's copy into the chosen folder, which is not the stash until the settings switch (`State` Move), or as Import stash…'s extraction into a new folder, which is not the stash until it is renamed into place (`State` Export stash…, Import stash…); no part opens an item's file in the root or `originals\` for writing. The store file and its journal are SQLite's alone, but for Move's and Export stash…'s copies of the store file between transactions, Move's removal of the old one after the switch, and Import stash…'s replacement of it with the whole folder (`State` Export stash…, Import stash…).
- **R3.** No part opens an original for writing; Media opens every item file read-only.
- **R4.** One routine in Media draws layers for the screen and for the file, and one encoder path serves the recorder, Save and the size estimate; the editor never draws a layer with Avalonia controls.
- **R5.** The clipboard is read only by Paste image, Ctrl+V in the window, and Stash clipboard image; nothing else reads clipboard data, and nothing listens for clipboard changes.
- **R6.** The Target seam sends one keystroke, Ctrl+V, after activation, and nothing else to any window.
- **R7.** Animations are decoded, drawn and encoded one frame at a time; the full-size frames of an animation a part holds at once are a fixed few, never a number that grows with the animation's length.
- **R8.** Derived data other than the finished pictures F6 places in the stash folder and Store's own files there (the store, its journal, `.work\`) lives in memory or under `%LOCALAPPDATA%\ImageStash`, never in the stash folder, and is never required to open a stash.
- **R9.** A notice or notification that says a change was made is raised after the transaction and file step that complete it, never before.
- **R10.** Nothing is added for sync, for a stash used from several PCs, for another platform, or for a capability the product specification does not name (L1); the export file (G36) carries a stash from one PC to another and serves nothing else.

## Product decisions settled here

- **P1.** Source: L1, "the layout of files ... inside the stash folder". The finished picture's file in the stash folder is named after the item (made safe for Windows, " 2" while taken), and renaming an item renames its files. User-visible: the file name a destination receives from a handoff or drag-out, and what File Explorer shows, is the item's name.
